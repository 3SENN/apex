# Apps, worlds and the cast

An app is a game or a tool that runs inside Atelier: a full page with Atelier as
its AI engine. It brings its own art, sound and characters, or borrows
Atelier's: your companions can play its characters, and the Atelier kit offers the
same art and shading the companions use. A world is a
place you build and share: props from the kit, your companions living in it
as residents, and spots that open apps. People make apps and worlds with a
companion in a chat, share them as files, links or through the community
index, and anyone can remix them.

The idea is that your companions are your characters everywhere. The same
Pip who answers your questions challenges you to a quiz, works the
counter in a friend's café world and cheers when you win, and looks the
same in every app because every app draws Pip with the same parts.

> **Status.** Everything here is built and proven in the real app except
> realtime multiplayer, Atelier Rooms and the Atelier pad (see *What's built*).
> Where a section describes something still to build, it says so
> (*planned*, *still to come*). Numbers marked as starting values are there
> to be tuned.

## Starting point

What Atelier already has, and what this design builds on:

- **Agent-built apps** (`src/shared/apps.ts`, `src/main/apps/`): one
  self-contained HTML file of at most 2 MB, built with `build_app`, run at
  `atelier-app://<uuid>/` in its own partition with no network and no
  `window.atelier`, versioned, listed under Workspace › Apps.
- **Packs** ([packs.md](packs.md)): the manifest, the sandbox and the
  `window.atelier` bridge, `test_pack`, signed `.atelierpack` files with trust on
  first use, update addresses, Remix and the community index. This design
  extends the pack format instead of adding a second one.
- **Companions** ([companion-system.md](companion-system.md)): rigs, parts and
  face layers generated by code in `scripts/companion-assets/`, assembled at
  runtime by `src/renderer/src/companion/` (plain three.js: `character.ts`,
  `animator.ts`, `materials.ts`, `face.ts`), with toon shading, outlines, the
  clips `idle listen think work talk alert celebrate sad sleep wave poke`, and
  an `anchor:prop` on the right arm.
- **Companion sharing**: Export… (`src/renderer/src/companion-card/ExportDialog.tsx`)
  saves a `.ateliercompanion` file with a share image beside it
  (`shareImage.ts`, 1200×630); opening or dropping one shows a review sheet
  (`companion-card/sheets.tsx`) with Add. The preset gallery at
  `atelier://presets` shows cards washed in each companion's colour.

## Principles

1. **One container, three faces.** Apps and worlds are packs. A pack whose
   main contribution is an app is shared as `.atelierapp`, one that holds only
   worlds as `.atelierworld`, anything else as `.atelierpack`. The bytes are the
   same signed zip; the extension picks the icon and the review sheet.
2. **Sharing feels like sharing a companion.** The same Export dialog shape
   (what to include, a note, a share image), the same review sheet, the same
   Add. The pack machinery (signatures, pinning, updates) stays underneath.
3. **The sandbox is the boundary.** As for packs: an app can reach exactly
   what its manifest asks for, checked in main on every call. That is what
   makes built, minified code acceptable in apps: the review shows what the
   app can do, not every line it contains.
4. **Atelier is the engine, not the art department.** AI, multiplayer rooms and
   the phone controller come from Atelier, so an app needs no API key and no
   backend. Characters, art and sound can come from Atelier too, but an app with
   its own uses its own: the cast and the kit are offers, never requirements
   (see *Assets*).
5. **Companions are the cast, never the data.** An app gets a companion's
   name and look. It never gets the personality, instructions, memory, chats
   or settings; when an app wants a companion to speak, Atelier writes the line.
6. **Worlds are data.** A world is JSON that places kit props and residents.
   It runs no code, so sharing one asks for no permissions beyond those of
   the apps it opens.
7. **Assets you may share.** An app ships whatever its author made, licensed,
   or took under an open licence, and asset packs from anyone can change how
   it looks and sounds. Everything in the kit is generated by code, like the
   companions. The community index takes any of that, never assets taken from
   someone else's game; files a player owns stay on their own computer.
8. **Atelier uses the format itself.** The world viewer and editor, the starters
   and the kit's examples are first-party packs.
9. **Everything is a plugin.** Atelier's extension points are surfaces,
   services and events that its own features and installed packs fill the same
   way, and everything a pack adds goes away with it (see *Everything is a
   plugin*). An app can become part of how your Atelier works, not just a tab.

## Everything is a plugin

Atelier has no privileged core that features patch. Its own features and its
packs are plugins of the same kind. A plugin contributes *services* (a
capability under a stable name), *events* (typed signals others observe) and
*registrations* (a tool, a row, a card) to a shared context. Every
registration has a disposer, and a plugin that needs a service starts only
once that service exists. So any part can be turned off, replaced or removed
without the rest knowing how it was built.

Plugins differ in one way that shapes the rest: Atelier's own features are
trusted code in the main process, while packs come from anyone. So Atelier has
two rings that meet at the same registries:

- **The core ring** is Atelier's built-in features (`src/main/features/`): trusted,
  in-process, wired through `Feature` hooks and registries that already return
  disposers (`registerClientTool`, `registerPageMenuSection`,
  `omnibox.registerProvider`).
- **The pack ring** is every installed pack, first-party or not. Pack code
  never runs in main or the chrome. It reaches the registries through its
  manifest (declarative contributions Atelier draws) and through the bridge
  (calls checked in main), from its own partition.

Each extension point is open to both rings, so a feature Atelier ships and an
app a companion builds plug in the same way.

### Surfaces

A surface is a place in Atelier that plugins fill, declared by the feature that
owns and renders it. A surface has a
cardinality and a way of drawing what fills it:

- **list**: any number of entries, ordered (sidebar rows, new tab cards,
  commands);
- **single**: one entry shows, the person picks which (the new tab page);
- **keyed**: one entry per key (a file type's opener).

An entry is either **drawn** (the pack gives data, and Atelier draws it with its
own components, so no pack code runs in the chrome) or **hosted** (the pack
gives a page, and Atelier hosts it in the pack's sandbox at that place).

| Surface | Cardinality | Entry | Today |
|---|---|---|---|
| `tab` | list | hosted: an app or panel in a tab | panels |
| `beside` | list | hosted: beside the page in split view | panels |
| `sidebar` | list | drawn: a row with icon, title and status | panels with `sidebar` |
| `newtab.cards` | list | drawn: lines from a module | cards |
| `newtab.page` | single | hosted: the new tab page itself, when the person picks it | – |
| `commands` | list | drawn: command bar rows | commands |
| `page.menu` | list | drawn: page, selection and link menu items | menus |
| `share` | list | drawn: Send to <app> for a page, selection, link or file the person picks | – |
| `open.with` | keyed by file type | drawn: Open with <app> in downloads and the file viewer | – |
| `chat.cards` | list | drawn: a card in a chat from structured data (an invite, a result) | – |
| `float` | list | hosted: a small always-on-top window | – |
| `settings` | list | hosted: the app's own section in Settings › Apps | – |
| `status` | keyed by entry | drawn: a short text, badge or progress on an app's sidebar row and tab | – |
| `world.places` | list | drawn: a place in a world that opens an app | – |
| `app.assets` | single, per slot | drawn: which asset pack fills one of an app's asset slots (see *Assets*) | – |

New surfaces are added by the feature that renders the location, listed in
this table and in the inspect catalog (below). A pack can't declare a surface
of its own in the chrome, but a hosted page can be a surface for other packs
through services.

### Services

A pack can provide services and use other packs' services. A service is a
name and a set of methods with JSON Schema inputs:

```json
"provides": [{
  "service": "story-library",
  "description": "The stories in Story Notebook.",
  "methods": {
    "list": { "input": { "type": "object", "properties": {} } },
    "append": { "input": { "type": "object", "properties": { "storyId": { "type": "string" }, "text": { "type": "string" } }, "required": ["storyId", "text"] } }
  }
}],
"uses": ["story-library"]
```

Atelier's built-in capabilities need no `uses`: they come with permissions
(`model` for `ai`, `cast` on the app, and so on); `uses` names other packs'
services only.

- A method runs in the provider's own sandbox: in its open app page if one
  is open (`atelier.services.provide(name, handlers)`), else in its tool host,
  which shares the app's storage because it is the same origin.
- Consumers call `atelier.services.call(service, method, input)`. Atelier routes the
  call between the two sandboxes, checks both manifests, and validates the
  input and the result against the schemas. Neither side sees the other's
  code or storage.
- Atelier's built-in capabilities share the namespace (`ai`, `cast`, `guide`,
  `files`, `notify`, `kit`; `rooms` and `pad` planned), so no pack can provide
  a service by those names. Each is a *capability seam* (a definition, a
  provider, consumers): the `ai` service has one definition and a provider
  per engine, and an app never knows which engine answered.
- **Starting on what it needs**: an app, panel or card whose `uses` are
  missing doesn't start. Its row shows why ("Needs Story Notebook", "Set up a
  model first") with the fix. When a provider goes away (turned off, removed),
  every entry that used it stops and comes back when it returns.
- **The companion uses services as tools.** With many apps installed, one tool
  per method would crowd every chat. A chat gets one `use_app` tool that finds
  methods by description and calls them, with each method's full schema loaded
  only when found; @-mentioning an app in the composer gives the chat that
  app's methods directly. A pack's `tools` stay as they are and count as a
  service the companion uses.
- Using another pack's service is a permission line on the consumer's review
  card ("Uses Story Notebook's story library"), and providing one is a line on the
  provider's.

### Events

`atelier.events.on(name, fn)` and `atelier.events.emit(name, data)`, with names
declared in the manifest (`"events": { "emits": ["achievement"], "on":
["atelier.theme"] }`).

- Packs only observe events. They can't intercept or change one, because a
  listener in another process can't sit in the middle of Atelier's work without
  slowing it down or holding it hostage. Interception (handlers that change
  an event or stop it) stays inside the core ring.
- Atelier emits `atelier.theme` (`{ dark }`) to packs that ask for it; more
  (`companion.mood`, `world.entered`, `app.launched`, `pad.*`) are planned.
  Nothing about your browsing is ever an event a pack can receive.
- Planned: Atelier listening to some pack events, so an `achievement` shows a
  toast and makes the companion celebrate. An app's row already updates
  through `atelier.status.set`.

### Reversible, per pack

Everything a pack adds lives in that pack's scope. Turning a pack off,
updating it or removing it disposes its scope and nothing else: its tools,
rows, cards, menus, services and listeners go, and entries that used its
services stop. `PacksRuntime.sync` keeps a key per pack (its files and whether
it runs): a pack whose key is unchanged keeps its registered tools, its tool
host, its cached new-tab cards and its compiled service schemas, and only a
pack that changed, went off, waits or went away has them taken down (and back,
if it runs). What is shared across packs by nature (skill names, which may
collide; site tweak rules; accents) is still worked out whole, which is cheap.

While a companion works on a draft, the draft runs from `dev/<id>/`, and each
`write_pack_file` reloads only what changed: an open app page reloads, its
contributions re-register. That is Atelier's hot reload.

### Composition

- A pack may require other packs (`"requires": { "packs": { "quiz-night":
  ">=0.3" } }`). A world requires the apps its places open; a bundle pack can
  contain nothing but requirements.
- A **setup** is a bundle pack that turns on a set of packs and picks the
  single surfaces ("Game night": the arcade, two worlds, a new tab page
  showing who's online). Profiles keep their own set of enabled packs, so a
  work profile and a play profile can be different browsers.

### Atelier's built-in features as packs

Where the public surfaces and services are enough, Atelier builds its features
as first-party packs: the world viewer and editor, the starters, the arcade,
and later sections of Workspace. A feature that needs something the public
surfaces lack adds that surface for everyone, not a private path. That keeps
the surfaces good enough for companions and community authors, because Atelier
depends on them itself.

The person can also make an app part of their own Atelier: pin it as a sidebar
destination, make it the new tab page (`newtab.page`), give it a keyboard
shortcut, let it open their files of a type (`open.with`).

### Inspect

Before writing code, a building companion calls `atelier_inspect` to read the
live catalog: every surface with its cardinality and what it draws, every
service with its methods and schemas, the events, the kit modules, and the
services of installed packs. The catalog is generated from the registries
themselves, so it can't drift from what runs. This is what keeps an agent
from writing against an API that doesn't exist, and it is the first thing
the build guide tells a companion to do.

## Layout on disk

App and world packs install like any pack (`<userData>/packs/installed/<id>/`,
drafts in `dev/<id>/`, see [packs.md](packs.md)). Added for this design:

```
<userData>/packs/budgets.json   each app's model budget and what it has used
<userData>/kit/<major>/         an older kit, downloaded the first time an app asks for it
```

An app runs inside its own pack: at `atelier-pack://<packId>/<root>/<entry>`, in
the pack's partition, `persist:atelier-pack-<packId>`. The app, the pack's
panels, cards and tool host are one origin, so they share localStorage and
IndexedDB: a new tab card can show the café's day, and the companion's tool
can read the game's save. Removing the pack clears the partition unless the
person chooses Keep saves. Today's single-file apps keep their
`atelier-app://<uuid>/` address and partition, so their saved state survives (see
*Today's apps*).

## The manifest

Manifest version 2 adds `apps` and `worlds`, and new permissions.
Version 1 manifests stay valid.

```json
{
  "format": "atelier-pack",
  "manifestVersion": 2,
  "id": "quiz-night",
  "name": "Quiz night",
  "version": "0.3.0",
  "description": "A quiz against a companion or a friend.",
  "author": { "name": "Senne" },
  "builtBy": "Pip",
  "updateUrl": "https://github.com/someone/quiz-night/releases/latest/download/quiz-night.atelierapp",
  "contributes": {
    "apps": [{
      "id": "main",
      "name": "Quiz night",
      "root": "app",
      "entry": "index.html",
      "build": "kit",
      "kit": 1,
      "kind": "game",
      "icon": "icon.svg",
      "orientation": "landscape",
      "cast": { "min": 1, "max": 2 }
    }],
    "worlds": ["worlds/quiz-hall.json"]
  },
  "permissions": {
    "model": true,
    "speak": true,
    "network": [],
    "notifications": false,
    "files": false
  }
}
```

Rules added to `validatePack`:

- `apps`: at most 5. `id`: `^[a-z0-9][a-z0-9-]{0,31}$`, like every pack item.
  `root`: the app's folder in the pack (default `app`); every file under it
  is served with the app CSP, everything else with the pack CSP. `entry`: an
  `.html` file under `root` (default `index.html`). Two apps' roots can't
  overlap. Files under `root` may have asset names with spaces and
  `& ' ( ) + , ! @ [ ] ~ =`, as games and build tools name them; paths the
  manifest names keep the stricter rule.
- `build`: `kit` (plain modules on the kit's libraries, readable, see below)
  or `bundled` (the output of any build tool). `kit` (the kit major, `1`
  today) is optional for either: with it, the app's pages get the import map
  for `three` and `atelier-kit/…`.
- `isolated: true` serves the app with COEP `require-corp` as well as COOP
  `same-origin`, for SharedArrayBuffer (threaded WASM: Godot 4, Unity and
  Emscripten builds with threads, some physics and audio engines). Off by
  default, because everything it then loads from a network host must allow it.
- `eval: true` lets the app's scripts run code they make while running
  (`eval`, `new Function`), which some older engines need; the review card says
  so (notice).
- `kind`: `game` or `tool`. Games may go full screen and lock the pointer
  without asking; tools open in a tab like any page.
- `orientation`: `any`, `landscape` or `portrait`. `cast.max`: at most 8.
- `model`: `true` (the default budget: 60 calls an hour, 500 a day per pack).
  `speak` needs `model`.
- Planned, and refused until they ship: `pad` on an app, and
  `rooms`, `realtime`, `devices` (camera, microphone) and a `model` budget
  object in `permissions`.
- `worlds`: at most 10 paths to world files (see *Worlds*).
- Limits for a pack that holds an app (starting values): 300 MB, 5,000
  files, 50 MB per file. The 1 MB reviewed-code budget and the minified-line
  rule apply to kit apps only. A bundled app's review card says that it
  contains built code that can't be shown, and lists what that code can
  reach.
- An app page's own inline scripts run: Atelier hashes each `<script>` in the
  HTML file as it serves it and allows exactly those, so a build tool's
  bootstrap (Next.js, Godot, Unity templates) works unchanged while a script
  injected later doesn't. Inline event handlers (`onclick="…"`) stay off.
  Panels keep the stricter pack rule: no inline code at all.
- Addresses resolve the way static hosts do. In a pack with one app, any
  address the pack doesn't use for its other files is the app's, so root paths
  (`/assets/app.js`) work without changing the build's base; a folder serves
  its `index.html`, `about` serves `about.html`, and a page address the app
  doesn't have serves the entry page, for a single-page app's routes.

## Two ways to build an app

**Kit apps** are what companions build, and what we recommend to people
writing apps by hand. Plain JavaScript modules, no build step, readable like
pack code. They import the kit's libraries by bare name:

```js
import * as THREE from 'three'
import { stage } from 'atelier-kit/scene.js'
import { character } from 'atelier-kit/character.js'
```

Atelier adds an import map to the entry page as it serves it, pointing those
names at the kit the manifest names (`/__atelier/kit/1/…`, inside the pack's own origin), and puts the map's
hash in the CSP. An app that pins `"kit": 1` gets exactly kit 1's versions,
whatever Atelier version runs it. Kit apps stay small (a few hundred KB of their
own code) because the libraries and art are not in the file.

**Bundled apps** are the static output of any build tool: Vite, Next's
static export, a Phaser or three.js project with its own copy of everything.
They are how existing web projects come in (see *Bringing a web project in*).
They can still load kit art by address (`/__atelier/kit/1/…`), use the
kit's CSS, and get companions as glTF models or sprite sheets from
`atelier.cast`; they can't use the kit's JavaScript modules, which need the
kit's own three.js.

## Assets

An app's look and sound come from three places, and it can use all three.

1. **Its own files.** Everything under the app's `root`: sprites, textures,
   models, audio, music, fonts, levels, video, in whatever names and folders
   its build uses (spaces and most punctuation are fine there). This is how
   most apps ship, and it needs nothing from Atelier: Atelier serves even a large
   game's assets straight from disk.
2. **Asset packs.** Separate packs, by the author or by anyone, that change an
   app's assets without touching its code: a texture pack, a skin, voices in
   another language, a level pack. The app declares what can be replaced, and
   the person picks which pack fills it.
3. **The person's own files.** Files the author can't ship, such as the data
   from a game the player owns, or the player's own photos and recordings.
   The app asks for them, the person picks them, and they stay on that
   computer.

The kit and the cast are a fourth, optional source: an app can use them for
some things and its own files for the rest.

### Asset slots and asset packs

An app lists the slots an asset pack may fill:

```json
"apps": [{
  "id": "main",
  "name": "Corner café",
  "root": "app",
  "build": "bundled",
  "kind": "game",
  "assets": [
    { "id": "art", "name": "Art", "description": "Sprites, furniture and the menu screens.", "layout": "app/assets/ui" },
    { "id": "voices", "name": "Voices", "description": "Customer and worker voice lines." }
  ]
}]
```

A pack fills one:

```json
"contributes": {
  "assets": [{ "id": "winter", "name": "Winter café", "for": { "pack": "corner-cafe", "app": "main", "slot": "art" }, "root": "winter" }]
}
```

- **Asset packs carry no code.** Their files are images, audio, video, fonts,
  models, JSON and plain text; `.html`, `.js`, `.mjs` and `.wasm` are refused.
  SVG is allowed and always served with `content-security-policy: sandbox`,
  so even framed as a page it runs nothing. Their review card says "Changes
  how Corner café looks" (info), and no other line.
- **The person picks.** Each slot shows on the app's pack page under *Look
  and sound*: the app's own files, or any installed pack that fills it. A slot
  is a single surface (see *Surfaces*): one pack at a time. Picking another
  reloads the app, so it never has to swap art while it runs.
- **The app reads the chosen pack in its own origin.** Slot ids are unique
  within a pack, and Atelier serves a slot's files at
  `atelier-pack://<appPack>/__atelier/assets/<slot>/<path>`, so the app loads them
  like its own (`fetch`, `<img>`, `<audio>`, textures).
  `atelier.assets.url(slot, path)` gives that address at once (no waiting, so it
  works in `src` attributes); a file the chosen pack lacks, or every file when
  none is chosen, comes from the app's own `<layout>/<path>`, so a pack can
  replace only some files. `atelier.assets.active(slot)` says which set is chosen
  (`{ pack, packName, set, setName }`, or null).
- **`layout`** (optional) points at the app's own folder that the slot
  mirrors, so a pack author can copy that folder, change files and keep their
  names. A slot without `layout` documents its files in `description` or a
  `README.md` in the app.
- An asset pack is a pack like any other: signed, shared as `.atelierpack`,
  listed in the community index under the app it is for, remixable. The
  app's page on Browse shows the asset packs for it.

### Your own files

`atelier.files.own({ accept, multiple, folder, note })` asks the person for files
of their own, with the app's note ("Choose the Assets folder from your copy
of the game"):

- Atelier copies them into the app's private space, `<userData>/packs/own/<packId>/`,
  and serves them at `atelier-pack://<packId>/__atelier/own/<path>`, same-origin, read
  only. The app sees nothing else on the disk.
- They are never part of the pack: Export, Share…, Remix, backups to others
  and the community index never include them. The app's details list them,
  with their size, and Remove.
- Asking for files needs `files` in the manifest, shown as "Asks you for
  files of your own" (notice).

That is how a remake of a game the player owns can ship its code without the
original's art: the player adds the files from their own copy, the way
OpenRCT2 and ScummVM work.

## The kit

The kit is what makes an app look like Atelier: the libraries, the art, the
interface pieces and the sounds, versioned together as one major. It is the
"texture pack", except that the companion look comes from flat colours, toon
shading and outlines rather than image textures, and the kit keeps it that
way.

Kit 1 today (built by `scripts/kit/build.mjs` into `out/kit/1/`, served at `/__atelier/kit/1/` in every pack's own origin):

| Part | What it is |
|---|---|
| `three`, `three/addons/…` | three.js 0.186.1, the companions' version, and the addons the kit lists (GLTFLoader, the meshopt decoder, BufferGeometryUtils, SkeletonUtils, OrbitControls) with what they import |
| `atelier-kit/character.js` | the companion runtime from `src/renderer/src/companion/`, bundled readable with three kept external: `character(look, { mood })` gives `object3d`, `bounds`, `update(dt)`, `setMood(mood)`, `move('walk' \| 'run' \| null, speed)`, `blink()` and `dispose()`, face included. `move` walks or runs over the mood with the steps matched to `speed` (units a second) |
| `atelier-kit/guide.js` | the person's companion in a corner of the app's page with a speech bubble: `guide({ corner, size })` gives `say(text, { mood })`, `quiet()`, `show(visible)` and `dispose()` |
| `atelier-kit/props.js` | `prop(id, { palette, tint })`: twenty props (trees, benches, tables, a house, a shop, stalls, a fountain, a table tennis table…) made from soft shapes in the companions' style and coloured from the palette; `PROPS` (names and footprints) and `PALETTES` |
| `atelier-kit/world.js` | `createWorldView(world)`: a world file as a three.js scene (tiled ground on an earth base, props, place outlines and names, the sky's light, background and fog), with `rebuild(world)` for an editor; `SKIES` |
| `atelier-kit/ui.css` | Atelier UI for apps: the browser's tokens (light and dark), Inter as an inline font, base type and the `ax-*` components (see [Atelier UI](#atelier-ui)) |
| `companion/` | the companion art the runtime loads, with its `LICENSE.md` ([Atelier Companion Art License](../ART-LICENSE.md); see *The cast*) |

| `atelier-kit/materials.js` | `toon(colour)`, `paint(name)`, `outline(mesh)`: the same 3-step gradient and inverted-hull outline as the companions |
| `atelier-kit/props.js`, later | toon-shaded, outlined props from modelled art (`props/<id>.glb`), replacing the shape-built ones under the same ids |
| `atelier-kit/scene.js` | `stage({ sky, ground })`: camera, lights, sky and ground presets that match how companions are lit |
| `atelier-kit/phaser.js` | loads cast sprite sheets and the props atlas into a Phaser scene |
| `atelier-kit/sound.js` | interface sounds and a small set of game sounds, synthesised in the page |
| `props/<id>.glb` | furniture, kitchen, sport, nature, buildings, food; each with `tint:` and `paint:` materials like companion parts, so worlds recolour them from a palette |
| `ground/<id>.svg` | flat tileable ground patterns (grass, boards, tiles, sand, water) in the palette |
| `atlas/` | the props rendered to sprite atlases for 2D games, at three sizes |
| `palettes.json`, `sky/<id>.json` | the companion palettes plus world palettes; sky and light presets |

How it is made:

- Props, grounds and atlases are generated by code in `scripts/kit-assets/`,
  next to `scripts/companion-assets/` and sharing its `lib/`, under the same
  rules: +Y up, 1 unit ≈ rig A's body height, flat base colours, glTF-Transform
  with meshopt, deterministic output committed to the repo. Budget per prop:
  under 60 KB and 4.5k triangles, checked by the asset test.
- Props meant for hands (paddle, racket, ladle, tray, ball) are modelled
  around the `anchor:prop` origin, so `hold(propId)` seats them like the
  companions' own props.
- Games need more clips than the browser UI uses. `walk` and `run` are built:
  posed on the rig in code (`src/renderer/src/companion/locomotion.ts`), so
  every rig and look has them, and the kit's `move()` plays them. Still to
  come: `jump swing throw catch sit fall cheer`, following the clip rules in
  [companion-system.md](companion-system.md) (loops seamless, one-shots
  about 1–1.5 s).
- Size target for kit 1: about 15 MB, shipped inside Atelier. Atelier ships the
  current kit and the one before it; an app asking for an older major
  downloads it once from the release server, checked by hash, into
  `<userData>/kit/<major>/`.
- The kit is served inside each pack's own origin (`/__atelier/kit/<major>/`),
  read-only, so module scripts and cross-origin-isolated apps load it as their
  own files, with no CORS or CORP headers needed. (The first design had an
  `atelier-lib://` scheme for it; same-origin turned out simpler.)

A new major comes only when a library's API breaks (three.js minor versions
do). Within a major, kit updates add props and fix bugs, never remove.

### Atelier UI

Apps a companion builds should look like Atelier, not like a generic AI demo.
Telling a model what to avoid mostly moves it to the next default, so Atelier
hands it the real thing instead:

- **The stylesheet.** `src/kit/ui.css` holds the browser's own tokens
  (surfaces, text, lines, the companion accent, state colours, space, radius,
  type, motion, focus) with the values of `src/renderer/src/styles.css`
  (`tests/appUi.test.ts` keeps them equal), base type in Inter and a small
  set of components: page column and header, sections, a card for one group,
  buttons (ink primary, companion accent, ghost, danger), fields, select,
  segmented control, switch, list rows, label and value pairs, table, empty
  state, badges, notices, progress and dialog. It all sits in cascade layers
  (`atelier.tokens`, `atelier.base`, `atelier.components`), so an app's own CSS always
  wins. The kit build adds Inter as a `data:` font (apps have no network).
- **build_app apps** get it first in their `<head>` as they're served
  (`src/main/apps/ui.ts`), with the accent of the companion that built them.
- **Pack apps** link `/__atelier/kit/1/atelier-kit/ui.css`; the starters do, and
  read canvas and scene colours from its tokens.
- **The design notes** (`src/shared/appDesign.ts`) ride in build_app's
  description and in the build guide's `design` part: the tokens, the
  components, how an Atelier app should feel, every state, numbers and words,
  and what makes an app look generic (gradients, glows, frosted glass, emoji
  icons, card soup, edge stripes, all-caps labels, hero numbers, centring
  everything). The built-in skill `app-design` has the long version with an
  example of every part.
- **The design check** (`lintAppDesign`) reads the app's HTML for those tells
  and for unlabelled controls and removed focus outlines. It never blocks:
  build_app reports what it found.
- **The look at the draft.** build_app opens the draft off-screen in its
  sandbox and returns it in light and in dark (`src/main/apps/preview.ts`),
  with any console errors, so the model sees what the person will see and
  fixes it before saying it's done.

The ideas in the notes and the skill draw on
public interface guidance: Impeccable by Paul Bakaus (Apache-2.0), Vercel's
Web Interface Guidelines (MIT), Anthropic's frontend-design skill
(Apache-2.0) and Google's DESIGN.md (Apache-2.0). No text is copied from
them.

## The cast

The cast is the companions an app may use as characters: yours, plus guests
who came with a world (see *Worlds*).

- `atelier.cast.members()` returns the cast the person last picked for this app,
  or their active companion when the app wants one and nothing was picked.
- `atelier.cast.pick({ min, max, title })` shows Atelier's character picker over
  the app (your companions, then guests), like a character select screen. The
  app never sees the companions that weren't picked.
- A member is `{ ref, name, rig, look }`. `ref` is opaque, stable for this
  app, and different in every other app, so apps can't match a companion
  across apps by id. `look` is the companion's rig, parts, face ids and colours
  (`CompanionLook`), nothing else.
- `atelier.cast.speak(ref, { situation, mood })` returns one line the companion
  would say, in character (needs `model` and `speak`). Atelier writes the prompt
  from the companion's personality in main; the app sends the situation
  ("you just lost a long rally 9-11") and gets back the line. The
  personality never reaches the app.
- Drawing a member: kit apps use `character(member.look)`. Planned for other
  apps: `atelier.cast.model(ref)` for a glTF with the clips, colours baked in and
  a face atlas per mood, and `atelier.cast.sprites(ref, { clips, angles, size })`
  for a sprite sheet and its frame data, rendered off-screen by Atelier the way
  stills and the Dock icon are.
- Multiplayer: an online app sends `member.look` to the other players (only
  part ids and colours), and each side draws it with its own kit. Planned
  with Rooms: `atelier.cast.guest(look)` to turn one received into a member,
  checked against `PART_IDS` and `FACE_IDS`.
- The guide is a kit module, `atelier-kit/guide.js`: the person's companion (the
  first member of the cast) in a corner of the app's own page with a speech
  bubble, the way the welcome flow has one beside each step. `say(text, {
  mood })`, `quiet()`, `show(visible)`. Useful for tools ("Pip walks you
  through it") and game hosts. The app decides what it says; Atelier's runtime
  draws who says it. (A chrome-drawn slot beside the app stays a later option.)

What an app never gets: the companion's id, personality, instructions,
memory, skills, chats, model settings, or the list of companions not picked.

**Characters in apps and worlds.** The companion art the kit draws with
(`companion/`, the parts and presets) is under the
[Atelier Companion Art License](../ART-LICENSE.md), and it allows what apps and
worlds do with it: draw the cast, ship characters made from Atelier's parts
(guests, residents, a host) in apps and worlds made for Atelier, sold ones
included, and give your brand a mascot inside Atelier, a character of your own
with a name and personality of its own. Not outside Atelier: the art and
characters made from it don't go into a game, site or product of your own
that runs elsewhere, and Atelier's six characters (Pip, Juniper, Bolt, Mochi,
Sage and Pepper) are never another brand's mascot
([TRADEMARKS.md](../TRADEMARKS.md)). An app that brings its own art and
characters is free to use them anywhere.

## Worlds

A world is a place: a grid of ground, kit props, named places, residents, a
sky, and spots that open apps. You walk around it as your companion,
residents go about their day, and stepping into a place opens its app with
the residents there as the cast.

```json
{
  "format": "atelier-world",
  "version": 1,
  "id": "harbour-town",
  "name": "Harbour town",
  "palette": "seaside",
  "sky": "late-afternoon",
  "size": [64, 48],
  "ground": { "base": "grass", "paint": [{ "type": "boards", "area": [10, 4, 22, 12] }] },
  "props": [{ "kit": "table", "at": [30, 0, 20], "turn": 90, "tint": { "accent": "#e8573d" } }],
  "places": [
    { "id": "hall", "name": "Town hall", "area": [26, 16, 38, 26], "opens": { "pack": "quiz-night", "app": "main" } },
    { "id": "cafe", "name": "Harbour café", "area": [8, 30, 20, 40] }
  ],
  "residents": [
    { "id": "r1", "home": "cafe", "role": "Runs the café", "guest": { "name": "Mochi", "look": { "rig": "A", "parts": { "head": "…" }, "face": { "eyes": "…", "brows": "…", "mouth": "…" }, "colors": { "skin": "#…", "hair": "#…", "accent": "#…", "outfit": "#…" } }, "personality": "…" } },
    { "id": "r2", "home": "hall", "role": "Quizmaster", "companion": "local" }
  ],
  "camera": { "at": [32, 18, 50], "lookAt": [32, 0, 24] }
}
```

- **Residents** are either guests (a name, a look and a personality carried in
  the file, never memory or instructions) or open spots (`"companion":
  "local"`) that whoever visits fills with their own companions. You walk
  around as your active companion, and the open spots get your other
  companions, in order, so the same companion never stands in two places.
  Your own worlds hold only guests and open spots, so sharing one carries
  nothing of your companions.
- **Places** are named areas. A place with `opens` launches that app in a
  tab, and `atelier.world.context()` there returns the world's name, palette and
  sky, the place, and the cast: you first, then the residents there. Guests
  get a ref of their own in that app and speak through `atelier.cast.speak` like
  companions, their lines written in main from the world's description of
  them. A place may open any pack's app: a world never waits for one.
  Stepping into a place whose app is installed but off turns it on; one that
  isn't here opens its pack page if the pack is installed, or Browse at that
  pack, which says plainly when no index offers it.
- **Residents talk** when you walk up to them (E, or a click):
  `atelier.worlds.speak` writes one short line in main, from the guest's
  personality or the companion's own, within the viewer's model budget.
  Nothing runs while the world isn't open.
- **The viewer and editor** are a first-party kit app, `atelier-worlds`
  (`src/firstParty/worlds/`). It comes off, so the browser looks and runs as
  before: no sidebar row, nothing loaded. It turns on when the person turns
  it on in Packs, or opens a world (a pack's Open), and then has a sidebar
  row. It lists
  your worlds and the ones packs bring (Harbour town comes with it); you walk
  with the keys or by clicking, and Enter steps into a place. Edit paints the
  ground (kept as a tile grid while you paint, written back as the fewest
  rectangles), places and turns props, draws places and links them to apps,
  adds guests and open spots, and sets the name, palette, sky and size, with
  undo, and asks before leaving with unsaved changes. A pack's world is
  copied into yours to change. Share… saves an `.atelierworld`: a signed pack
  holding just the world. The viewer speaks the person's language (its own
  small table in `app/i18n.js`, English and Dutch for now), and residents
  answer in it.
- **atelier.worlds** is the surface the viewer uses (`permissions.worlds`, a
  notice on the review): `list`, `get` (with who fills the open spots),
  `save` (yours; `{ copy: true }` for a new id), `remove`, `apps`, `enter`,
  `speak`, `share`, `find` (an app a place opens that isn't here). Any pack may ask for it; Atelier's viewer has no private path.
- **Limits** (starting values): 2 MB per world file, 5,000 props, 2,000
  painted areas, 64 places, 32 residents, 8 to 128 tiles a side, kit props
  only, 10 worlds a pack, 100 worlds of your own.
- **Companions build worlds** by writing the JSON with `write_pack_file`
  (the build guide's `worlds` part); `test_pack` checks every world file and
  returns a still of each (the first two), drawn off-screen in the test
  sandbox from the world's own camera, so the companion looks at what it
  made.

## Freedom

The sandbox decides what an app can *reach*, never what it can *do*. Inside its
own origin an app is a full web page with nothing taken away:

- any framework, engine or build tool, and code of any size;
- WebGL 2 and WebGPU, WebAssembly (with threads under `isolated`), workers,
  audio worklets, its own frames;
- full screen, pointer lock and gamepads for games;
- lots of storage: IndexedDB and the origin private file system in its own
  partition, with `navigator.storage.persist()` granted.

Reaching anything outside is always a permission, shown in plain words, and
there are many to ask for: network hosts, reading pages, the model, the
cast, notifications, the clipboard, files, folders, your own files, camera and
microphone, rooms and the pad, connectors, sign-in, other packs' services,
surfaces. Nothing is off-limits because Atelier didn't think of it; what isn't
here yet is a capability to add for everyone (see *Atelier's built-in features as
packs*).

- **Ask when needed.** Besides what the manifest lists, an app may declare
  `optionalPermissions` and ask for them at the moment a feature needs them:
  `atelier.permissions.request({ network: ['api.example.com'] })` shows the same
  plain-words lines, and the answer is remembered and revocable in the app's
  details. An app installs with a short card and grows when the person wants
  what it offers.
- **Developer mode.** Packs › *Load a folder…* (wherever the organisation
  allows sideloading): the pack runs straight from a folder on disk, reloads
  when a file changes and needs no signature. Nothing loaded this way is
  shared until it is exported.
- **No gatekeeper.** Files, links and any index work, and the community index
  is one index among many. Limits exist for safety and size, and an
  organisation can raise or lower them (see *Apps for organisations*).

## Fast by default

- **Its own process.** Each pack is its own origin, so Chromium's site
  isolation gives it its own renderer: a heavy game doesn't slow the chrome or
  other tabs, and a crash takes only its tab.
- **Files straight from disk.** An app's files aren't held in Atelier's memory.
  Small files are read in one go; anything over 256 KB streams, and byte
  ranges let audio and video seek. The `atelier-pack` scheme has V8's code cache,
  so a big bundle compiles once.
- **Start-up stays quick.** The check that an installed pack's files haven't
  changed runs in the background after start-up, not before the first window.
- **The GPU is there.** WebGL 2 and WebGPU, `powerPreference:
  'high-performance'` honoured.
- **Background.** A hidden app tab is throttled like any tab and can sleep
  with the others, hardened again when it wakes. A game that keeps time (a
  café that cooks while you're away) catches up from the clock on resume and
  uses scheduled notifications; nothing needs to run hidden.
- **Watched, not capped.** Chromium can't hard-limit a page's CPU, so Atelier
  watches each pack's process (memory, CPU, energy) and shows "<App> is using
  a lot of energy" with Pause when it runs hot in the background. The
  app's details show its use; the playtest reports frame times.

## Apps for organisations

The same format holds a team's tools: a dashboard over the company's APIs, a
helper beside the CRM that reads the customer's page, an approval flow, a
field tool, onboarding and training. What a business needs on top:

**Reaching company systems**

- `network`: the company's API hosts, reached directly from the app.
- `auth`: sign-in through Atelier (`src/main/packs/signIns.ts`). The manifest
  names the identity provider (`"auth": [{ "id": "corp", "name": "Contoso
  account", "issuer": "https://login.example.com", "clientId": "…", "scopes":
  ["openid", "email", "api.read"], "hosts": ["api.example.com"] }]`). Atelier
  finds the provider from its issuer (RFC 8414, or OpenID discovery), runs the
  authorization code flow with PKCE in a tab of the person's profile (so a
  company sign-in they already have carries over) with the loopback redirect
  the connectors use (`src/main/connectors/oauth.ts`), and keeps the tokens in
  `packs/pack-signins.bin`, encrypted with the system keychain like the keys.
  The access token goes in `Authorization: Bearer` on the app's requests to
  those hosts (fetch, WebSocket handshakes, images, `atelier.fetch`) and is taken
  off a request anywhere else; it is refreshed when due. App code never sees a
  token: `atelier.auth.status()` gives `{ corp: { signedIn, user } }` (the ID
  token's email, username or name), `atelier.auth.signIn('corp')` opens the
  sign-in and resolves once it's done (closing the tab cancels it, and the
  app's tab comes back after), `atelier.auth.signOut('corp')` forgets it. The
  pack's page lists its sign-ins with who is signed in, Sign in and Sign out.
  Rules: a public client (no secret) that allows `http://127.0.0.1/callback` on
  any port; an https issuer (http only on this computer while you develop),
  without a query; every host in `network` or `optionalPermissions.network`; at
  most 4; and a host never gets both a sign-in and a secret in
  `Authorization`. The review says "Signs you in to login.example.com and sends
  that sign-in to api.example.com"; an update that changes the issuer or the
  hosts asks again. A test run never signs in.
- `connectors`: the person's MCP connectors, used by the app, so a tool
  builds on what is already connected. The manifest names them in
  `permissions.connectors` by directory id (`atlassian`, `github`) or a
  server's name; the review says "Uses your connectors: atlassian, github",
  and a new one asks again. `atelier.connectors.status()` gives `{ atlassian: {
  connected, name } }`, `tools(ref)` the tools the person has on, and
  `call(ref, tool, input)` runs one in main (remote or local, through the
  connector's own session) and returns `{ text, data, isError }`. Each tool
  runs as the person set it in Connectors: off refuses, "ask" asks them every
  time, and a local server needs its approval. `connect(ref)` opens
  Connectors at that service; the pack's page lists the connectors it uses
  with Connect… for one that isn't connected. The app never sees an address
  or a credential, input is checked against the tool's schema, the audit log
  records each call (connector and tool), and the permission ceiling can
  limit which connectors packs may use (`connectors: ["atlassian"]`). A test
  run uses none.
- `sites`: reading the company's own web apps the person has open, as packs
  already can.
- `ai`: on the person's account, or the organisation's own model gateway when
  `AiProvider` sets one (below).

**Distributing inside a company**

- A private index: an https file on the intranet, or behind the company's
  sign-in. A `PackIndexes` entry can be `{ "url", "name", "auth": { "issuer",
  "clientId", "scopes" } }`: Browse reads it only once someone has signed in,
  and until then shows "Contoso apps is your organisation's. Sign in with
  login.contoso.com to see what it offers" with Sign in, which runs the same
  sign-in as apps. The token goes on every request to the index's own origin
  (the index, its archives and pictures, updates) and nowhere else, a
  redirect elsewhere leaves it behind, and an index that refuses it (401,
  403) offers Sign in again.
- Packs signed with the organisation's key. `PackTrustedKeys` names the
  organisation's keys: their packs are allowed even under a short allowlist,
  and the review says "Signed by your organisation". As for any signed pack,
  the first key to install an id is pinned, so no other key can replace it.
- Enterprise policies
  (`src/main/packs/policy.ts`): Group Policy on Windows
  (`HKLM\SOFTWARE\Policies\Atelier`, then `HKCU`; the machine's wins), a
  configuration profile on macOS (`com.atelier.browser`, read with plutil),
  `/etc/atelier/policies.json` on Linux. Lists and objects are JSON text in a
  registry string, booleans a DWORD. They are read in the background, never
  in the way of start-up, and apply the moment they are found; without one,
  every rule is a no-op and nothing is read again. Each value is checked on
  its own, so a bad value voids only itself (and goes to the log).
  - `PackIndexes`: the indexes Browse reads; no others can be added or
    removed (Browse says the organisation chooses them); an entry with `auth`
    is a private index (above);
  - `PackForceInstall`: addresses (with an optional `sha256`) of packs that
    are installed, on, and can't be turned off or removed; their pages say the
    organisation installed them;
  - `PackAllowlist` and `PackBlocklist`: by pack id, `key:<key id>` for an
    author key, or `*`; the allowlist and trusted keys win over the
    blocklist, so `["*"]` blocked and a short allowlist is "only these";
  - `PackTrustedKeys`: the organisation's signing keys: their packs are
    allowed;
  - `PackPermissionCeiling`: how far no pack may go: `network` and `sites` (the
    hosts allowed), `model`, `files`, `notifications`, `clipboard`,
    `pageScripts`, `secrets`, `localConnectors`, `connectors` (the ones packs
    may use), `server` (`false`: no app runs a web server) and `serverLan`
    (`false`: web servers on this computer only, never on the Wi-Fi); optional
    permissions count;
  - `PackSideloading`: `false` lets packs in only from indexes; the Packs page
    then offers no file, link or folder install and says why;
  - `AppConfig`: per pack, the values of its `env` (tenant address, feature
    switches; only names the pack declares) and `secrets` (a service token),
    set by the organisation and read-only to the person: the pack's Keys show
    "Set by your organisation", and the app reads `atelier.env` as always and
    never sees a secret. And its sign-ins' `issuer`, `clientId` and `scopes`
    (`"auth": { "corp": { "issuer": "https://login.microsoftonline.com/<tenant>/v2.0",
    "clientId": "…" } }`), so one published app signs in to each company's
    own tenant; the pack's page says "Set up by your organisation".

  Blocked, not allowed and over the ceiling hold for what is installed too: such
  a pack stops, and its page says why. Where a pack may come from (sideloading,
  the indexes) holds for installing, so a pack already here keeps
  working. Force-installed packs, and packs Atelier brings, are always let in. A
  review shows the organisation's reason as a problem, so Install is never
  offered for something the policy refuses.

  - `AiProvider`: the organisation's own model gateway, any endpoint that
    speaks Anthropic's Messages API (`{ "url": "https://ai.contoso.example",
    "token": "…", "models": { "fast": "…", "smart": "…" } }`, with a `key`
    for `x-api-key` or a `token` for `Authorization: Bearer`, one of them).
    Every model call a pack makes (`atelier.ai`, `atelier.ask`, the cast's and the
    residents' lines) goes there instead of the person's account, under the
    same budgets, with the gateway's names for the fast and smart tiers when
    it gives them; the Packs page says apps use the organisation's AI
    service. Atelier's chats are untouched.

**Data and compliance**

- An app's data stays in its partition on the device; removing the app removes
  it.
- Each pack's log records bridge denials and tool calls. With `PackAuditLog`,
  it also records each permission used, the hosts its app connected to, and
  where its keys and sign-ins went (once per host every ten minutes), and
  can't be cleared; Save log… writes any pack's log to a file.
- Nothing about an app goes to Atelier's servers.

## The sandbox

Apps reuse the pack sandbox (`src/main/packs/sandbox.ts`): the pack's own
partition, served only from the pack's files and the kit inside its own origin. Files
under an app's `root` get a wider CSP, and the app's pages get more
permissions.

| | Pack panels and tools | Apps |
|---|---|---|
| Scripts | the pack's readable files | the app's files and the kit; bundled code for `bundled` apps |
| Workers and WASM | no | yes (`worker-src 'self' blob:`, `'wasm-unsafe-eval'`) |
| Frames | no | the app's own pages only |
| Network | `atelier.fetch` through main | the hosts in `network`, straight from the page (fetch, WebSocket, EventSource, images, media), and `atelier.fetch`; see *Your own servers* |
| WebRTC | removed from the page | removed for now; later with `realtime`, through declared ICE servers or Rooms (IP policy `default_public_interface_only`) |
| Camera, microphone | denied | declared in `devices`, asked the first time, revocable in the app's details |
| Full screen, pointer lock, gamepad | denied | allowed for games |
| Downloads | denied | `atelier.files.save` with `files` |
| SharedArrayBuffer | no | with `isolated: true` (COOP `same-origin` and COEP `require-corp`) |
| Size | 10 MB | 300 MB |

CSP for apps:

```
default-src 'none'; script-src 'self' 'wasm-unsafe-eval' ['unsafe-eval' with eval] 'sha256-<each inline script of the page>';
style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: <hosts>; font-src 'self' data:;
media-src 'self' data: blob: <hosts>; connect-src 'self' data: blob: <hosts, with wss>; worker-src 'self' blob:;
frame-src 'self'; child-src 'self' blob:; object-src 'none'; form-action 'none'; base-uri 'none'
```

(`appCsp` in `src/main/packs/sandbox.ts`. `<hosts>` is each host in `network`
and `optionalPermissions.network` as `https://host:*`, plus `wss://host:*` in
`connect-src`, and `http`/`ws` for `localhost` and `127.0.0.1`; a wildcard
host covers its base name too. Code, styles, fonts and frames never come from
a host. `mediastream:` joins with camera, later.)

Unchanged from packs:

- no Node;
- no navigation away and no pop-ups;
- no cookies, and partitions are never browsing sessions;
- the agent never acts inside an app;
- every bridge call is checked in main.

Apps have no `sites` permission at all: an app can't read your pages, so the
data it could send anywhere is its own, the cast's looks and the model's
answers. The `atelier-pack` scheme gains `stream` so audio and video seek.

Big packs aren't held in memory. The store keeps a pack's manifest, code and
small files in memory as today, and reads the rest from disk when served;
the hash check that catches files changed on disk runs in the background
after start-up instead of blocking it.

## Your own servers, keys and settings

Apps connect to their own servers, and the person's own accounts, without
Atelier in the middle and without a key ever being in the pack.

**Reaching a server.** An app's pages connect straight to the hosts in
`permissions.network`: `fetch`, `WebSocket`, `EventSource`, images and media,
over `https` and `wss` (and `http` and `ws` on `localhost` and `127.0.0.1`),
on any port. The rules are the web's: the page's origin is
`atelier-pack://<pack id>`, so the server answers CORS for that origin (or `*`),
and a request with its own headers is preflighted. That is what lets a
framework's own client (a REST or GraphQL client, socket.io, Supabase's or
Firebase's SDK) run unchanged. `atelier.fetch` stays for panels and tools, and
for an app that wants it: it runs in main, so it needs no CORS, sends no
cookies, and returns text up to the fetch limit.

Underneath, four things hold an app to its hosts, so a host only listed as
optional stays closed until the person grants it, and closes again when they
take it back:

- the CSP names every host the pack may ever reach (so a grant works without a
  reload);
- the session's webRequest lockdown lets through only the hosts it may reach
  now;
- the session's own `http`, `https`, `ws` and `wss` handlers refuse everything
  while a pack has no hosts;
- the proxy is still a dead end, with the hosts it may reach now on its bypass
  list, so a preconnect or DNS prefetch to anything else goes nowhere.

WebRTC stays removed: Rooms (and `realtime`) bring it back later, through
servers Atelier knows. A pack without an app (panels, tools) never connects
straight; its pages' CSP doesn't allow it.

**A pack is public, so a key never goes in it.** Everyone who installs a pack
has every file in it. A key in a pack is a key for all of them, so:

- your own keys (your database, your payment provider, the model API your
  server calls) stay on your server, and the app talks to your server;
- export and Share… refuse a pack with a `.env` file, or with text in a
  known key format (Anthropic, OpenAI, AWS, GitHub, Slack, Stripe secret and
  restricted keys, SendGrid, Google OAuth client secrets, private keys,
  Supabase service-role tokens), naming the file; hand-written code is also
  checked for `password: "…"` and the like. Keys meant to be public pass: a
  Firebase web config's `apiKey`, a Maps browser key, a Supabase anon key,
  Stripe's `pk_`;
- `validatePack` refuses a `.env` file anywhere in a pack, and a linked folder
  never reads `.env`, `.env.*` or `.npmrc` into one.

**Keys the person brings: `secrets`.** When the app works with the person's
own account somewhere (their API key for a service, a token for their
company's API), the manifest says so:

```json
"secrets": [
  {
    "id": "ACME_KEY",
    "name": "Acme API key",
    "description": "From acme.com › Settings › API.",
    "hosts": ["api.acme.com"],
    "header": "Authorization",
    "prefix": "Bearer "
  }
]
```

- The review card says it: "Asks you for Acme API key and sends it only to
  api.acme.com (the pack's code never sees it)". An update that sends a key
  to a new host asks again.
- The person enters it on the pack's page (Keys). Atelier keeps it in the system
  keychain (`safeStorage`, one encrypted file, `packs/pack-keys.bin`), never in
  the pack's partition, and removes it with the pack.
- Atelier puts it in that header on every request to those hosts: the app's own
  `fetch`, a WebSocket's handshake, images, `atelier.fetch`, replacing whatever
  the page set there. On a request to any other host the header is taken out
  again, and `atelier.fetch` works it out hop by hop, so a redirect never carries
  a key on.
- The app only learns whether there is one: `atelier.secrets.status()` gives
  `{ ACME_KEY: true }`. Without one, `atelier.secrets.request('ACME_KEY')` opens
  the pack's page at that key and resolves `{ set: true }` once the person
  saves it (or `{ set: false }` after ten minutes). Then the app just calls the
  API.
- Rules: `id` like an environment variable (`^[A-Z][A-Z0-9_]{0,63}$`); at most
  10; every host in `network` or `optionalPermissions.network`; not in a header
  the browser owns (`Cookie`, `Host`, `Origin`, `Content-Type`, `Sec-*`,
  `Proxy-*` and the like); a `prefix` of at most 40 characters with no control
  characters. A value is one line, up to 8,192 characters.
- What it doesn't protect from: a host that echoes requests back would show
  the key to the app. Bind a key only to the service it is for.
- A test run (`test_pack`) has no keys.

**Public settings: `env`.** Values that aren't secret but differ between
builds or installs (the server's address, a feature switch) go in the
manifest's `env` and reach every page of the pack as `atelier.env`:

```json
"env": { "SERVER_URL": "https://api.myapp.com", "REALTIME": "on" }
```

At most 50, each up to 2,000 characters, named like secrets and never the same
name as one. A value in a known key format is refused: env is public.

**While you develop.** A pack loaded from a folder (Packs › Load a folder…):

- its `.env` and `.env.local` (later wins) fill `env` values and `secrets`
  with the same names: the names the manifest declares and no others, since
  the same folder often holds your server's own `.env`. A key entered on the
  pack's page wins over the file; the page shows which one is used ("From
  .env");
- its app may reach `localhost` and `127.0.0.1` without listing them, so
  `SERVER_URL=http://localhost:8787` in `.env` points it at your own server,
  and the published pack carries no `localhost` permission;
- editing `.env` reloads the app like any other file.

**Organisations.** An organisation's `AppConfig` policy fills `env` and
`secrets` for its managed packs, and `auth` signs people in and adds the
token the same way a secret goes on (*Apps for organisations*).

## Atelier as the AI engine

`atelier.ai` runs on the engine the person chose: their API key or their Claude
Code sign-in. App authors ship no key and run no server, and the person
always knows whose account pays.

- `ask(prompt, { system, tier, maxTokens })` returns text. `tier` is `fast`
  or `smart`; Atelier maps it to models (Haiku and Sonnet today), so apps don't
  break when models change, and a model name is refused.
- `stream(prompt, { onText })` calls `onText` with each piece as it arrives
  and resolves to the whole reply. With an API key the pieces come as the model
  writes; on other engines the reply arrives in one piece. (A callback, because
  Electron's context bridge can't carry async iterators.)
- `json(prompt, { schema })` returns a value that fits the JSON Schema:
  structured output where the engine can, checked with ajv, asked once more
  when it doesn't fit.
- `decide(state, questions)` answers typed questions (`noul`: yes or no,
  `choice`: one of up to 64 options, `score`: a level on a 2 to 10 step
  scale) with probabilities and no text (docs/decisions.md). On the person's
  decision model (Settings › Quick decisions) it answers in about a tenth of
  a second and has its own budget, 600 an hour and 5,000 a day; without one,
  their Claude engine answers within the model budget and `source` says
  `claude`, whose stated confidence is less calibrated.
- `session({ system, tier, tools })` holds a conversation; `send(text)`
  resolves to the model's answer. `tools` are the app's own (`name`,
  `description`, `input`, and `run(input)`, which runs in the page); when the
  model calls one, its answer goes back to the model. Atelier runs the loop, at
  most 8 tool rounds per message, and the history stays in the page
  (`history()`). With an API key the tools are Messages API tools; on an
  engine whose one-shot calls carry no client tools, each round is one call
  that answers in JSON (a tool to use, or the reply), constrained by a JSON
  Schema where the engine takes one. The history has the Messages API's shape
  on every engine, so a session carries over when the person changes
  engine. Web search for sessions is planned, with its own permission line.
- A session has nothing but the app's tools: no browser, no memory, no
  connectors, no Atelier tools, and no companion persona unless it is a
  `cast.speak` call, which Atelier composes itself.
- **Budget.** Every model call of a pack counts, `atelier.ask` and each round of
  a session alike: 60 calls an hour and 500 a day (starting values), with a
  clear error past them. Next: tokens per day, shown on the review card in
  plain words and adjustable in the app's details. A manifest asking for more
  shows it on the card; an update that raises it waits for approval. Use
  counts under Apps in the usage meter, per app. An app over its budget gets a
  clear error to show, never a silent failure.
- Model output is untrusted to the app, and anything an app sends (including
  what other players typed) is untrusted to the model; since a session can
  reach only the app's own tools, what a bad prompt can do stays inside the
  app.

## Multiplayer, Rooms and the Atelier pad

Three ways to play together:

1. **Atelier runs a server for the app, on this computer.** Works today:
   `permissions.server` with `lan` and `atelier.server.start({ lan: true, root })`
   ([packs.md](packs.md) › A web server of its own). Phones and computers on
   the same Wi-Fi scan the app's QR code, open a page of the pack over https
   with Atelier's certificate (so phones give motion sensors), and talk to the
   app's page over a socket; Atelier's bar over the app says it is sharing and has
   Stop. The `phone-controller` starter is a working example. Nothing leaves
   the local network.
2. **The app brings its own server.** Works today: a `network` host
   (`wss://…`) for rooms, game state and signalling, reached straight from the
   app (*Your own servers*). WebRTC between players follows with `realtime`.
   Nothing in Atelier needs to run.
3. **Atelier Rooms** (later: a paid service Atelier runs, which people and studios
   can buy). A hosted relay and signalling service: `atelier.rooms.create()` gives a
   four-letter code and an invite link (`atelier://apps/<packId>?room=CODE`);
   messages go through the relay and upgrade to a direct WebRTC data channel
   when the network allows, with TURN as the fallback. Rooms carry app
   messages and looks, never anything else.

**The Atelier pad** turns a phone into a controller without the app writing a
phone page. A phone can't open `atelier-app://`, so Atelier serves one standard
controller page from the Rooms host over trusted https (phones only give
motion sensors to secure pages). `atelier.pad.pair()` shows a QR code that Atelier
draws over the app; the phone opens the pad, asks for motion access where the
phone requires it, calibrates, and shows the layout from the manifest's `pad`:
motion (orientation and acceleration at 60 Hz), up to six buttons, a stick, a
touchpad, vibration. Events reach the app through `atelier.pad.on`. No app code
ever runs on the phone.

## Companions as builders

The pack tools in [packs.md](packs.md) build apps too, so companions learn one
set of tools:

- `create_pack(id, name, description, starter?)`: with a `starter`, the draft
  starts from a working kit app (`src/main/packs/starters.ts`): `game-3d`
  (three.js with the person's companion as the player), `game-2d` (canvas),
  `tool` (`atelier.ai.stream`) and `story` (`atelier.ai.session` with a tool, and
  the companion's lines). Each is one readable module that already follows
  the rules and calls the test hook. Later: Phaser, Preact and Rapier starters
  once the kit has them, and a `party` starter with Rooms and the pad.
- `atelier_inspect({ guide })` returns one part of the build guide (apps, kit,
  cast, ai, servers, worlds, services, files, assets, notifications,
  sharing); `create_pack`'s
  own guide stays short and points at them (see *Creator mode*).
- `write_pack_file` and `read_pack_file` as today.
- `test_pack(id, { playtest })` loads an app off-screen (default 1280×720) in a
  throwaway sandbox, as `test_pack` does for panels, and runs a script of steps:
  `{ wait }`, `{ key, holdMs }`, `{ click: [x, y] }`, `{ type }` and `{ capture }`
  (pointer paths and pad samples later). It returns:
  - problems and console errors;
  - up to 8 captured frames, as images the companion looks at;
  - frame times (average and 95th percentile);
  - the states the app reported through `atelier.test.ready`.

  `ai` and `cast.speak` return stand-ins unless an installed version of the
  pack may use the model, as `atelier.ask` does in tests today. The cast is
  filled from the presets.
- `propose_pack(id, note)`: the card shows the app's still and Review and add.
- `build_app` stays for quick single-file apps.

The frames reach the model as images on every engine: a client tool's result
may carry pictures (`ClientToolResult.images`, at most 8), which become image
blocks after the text with the API key and MCP image content on an engine that
reaches the tools over MCP.

## Creator mode

In Creator mode a companion builds apps and packs for the person. It rests on
these rules:

- **One lifecycle.** An app or pack a companion makes goes through exactly the
  path a person's own install does: a draft, `test_pack`, `propose_pack`, the
  review card, Install. There is no separate lifecycle for generated code
  (no run-before-install, no standing approval of future versions). A
  companion never installs or grants anything.
- **Look before writing, read-only.** `atelier_inspect` lists the live surface
  (window.atelier, surfaces, services, events, limits) and is kept in step with
  the bridge by a test that checks it against the source. It changes nothing
  and needs no approval.
- **Guidance in parts.** The build guide is a short core plus parts loaded on
  demand (`atelier_inspect({ guide })`), each well under the size at which a long
  tool result is cut. Builder text never goes in the system prompt, which
  every turn pays for.
- **Start small, verify for real.** Starters give a working first version;
  `test_pack`'s playtest plays it in the real sandbox and returns frames, so
  the companion checks what the person will see rather than a mock.
- **Results that say what's next.** Every builder tool's result has a `next`
  sentence.
- **A real sandbox.** What a companion builds is a pack like any other: it
  never runs in main or the chrome, and the review card shows what it can
  reach.
- **Errors come back to the companion.** `test_pack` returns console errors,
  frame times, frames and the pack's log, and Atelier keeps each pack's log.
- **Approval is the review card**, not a per-call prompt on a manager tool:
  `propose_pack` hands the person the same card any install shows.

**Creator chats.** The builder is a mode of a chat with its own entry points,
not part of every chat:

- Chats started from New app, New pack, Edit or Remix are Creator chats
  (`startChat(…, { creator: true })`): the builder tools (`create_pack`,
  `write_pack_file`, `read_pack_file`, `test_pack`, `propose_pack`,
  `list_packs`, `atelier_inspect`) are frozen in from the first message, with the
  build guide as context.
- Every other chat has one small tool instead, `creator_mode`. When the person
  asks for an app, a game or a pack, the companion calls it; its result carries
  the guide and changes the chat's setup (`ClientToolResult.setup`), and the
  builder tools join the chat. With an API key they are there at the next step
  of the same turn. An engine that takes its tools only when its process
  starts ends the turn with a sentence, and Atelier goes straight on in a fresh
  process that resumes the conversation with them.
- A chat is a Creator chat when `create_pack` is in its frozen tools, so the
  mode needs no new field in the chat file, and chats from before the mode keep
  their builder. Private chats, routines and delegated children never build.

**New tools in a running chat.** A chat freezes its tools at its first message
so its cached prefix stays valid. Two things are the exception: at the start
of each turn, the tools of a pack the person installed or turned on since
(`pk_…`) join the end of the list; and when `creator_mode` runs, the builder
tools join. Either way the next request misses the cache once, and Claude
Code relaunches with them. A chat that gained no pack and never asked for
the builder stays exactly as it was, older chats included; tools of other
groups never change mid-chat, and a pack removed mid-chat simply drops out of
the request.

- **Inspection in two steps.** `atelier_inspect({ list: true })` gives a short
  directory of names (calls, surfaces, services, events, guide parts), then
  `atelier_inspect({ query: "connectors call" })` the exact entries matching
  every word; `what` still gives whole parts.

Agent quality comes mostly from this loop: one small, stable kit that the
model knows (three.js, Phaser and Preact are all well known), starters that
already follow the rules, and a playtest that shows it the result instead of
leaving it to guess. Every starter calls `atelier.test.ready` with its game
state, so companions keep the hook.

## Sharing

Sharing follows the companion flow (`ExportDialog.tsx`, `shareImage.ts`,
`companion-card/sheets.tsx`):

- **Share…** on an app or a world opens a dialog shaped like companion
  Export:
  - **App**: a note (up to 500 characters) and the share image: the app's
    still on a wash of its icon colour with its name, 1200×630, drawn like the
    companion's. It saves `<id>-<version>.atelierapp` with `<id>.png` beside it.
  - **World**: switches for *Bring residents along* (on: your companions
    there travel as guests with their name, look and personality, never memory
    or instructions; off: they become open spots) and *Include the apps its
    places open* (off: the receiver gets each one from its own link; on: their
    packs travel inside, signatures unchanged), a note, and a share image from
    the world's camera with the residents in frame. It saves
    `<id>-<version>.atelierworld`.
- **Receiving**: double-clicking, dropping on Atelier, or Install from a link
  shows a review sheet like a companion import: the still, the name, the
  author and key fingerprint, the note, and the permission lines from
  `describePackPermissions`. A world also shows its residents standing in a
  row, and each place with the app it opens (Get for missing ones). Add
  installs it. A world's open spots ask which of your companions move in, with
  Skip.
- **New permission lines**:
  - info: uses your companions as characters (names and looks); opens full
    screen;
  - notice: schedules notifications; saves files you choose;
  - warning: uses your model account (with its budget in words); has your
    companions speak in this app; uses the camera or microphone; reads and
    writes a folder you choose; plays online through Atelier Rooms;
  - danger: sends data to listed hosts while it can use the camera or
    microphone, or a folder you chose.
- **Under the hood**, everything in [packs.md](packs.md)'s *Sharing* applies:
  the hash, the Ed25519 signature, trust on first use, the streamed unzip,
  update addresses (a wider budget or a new device counts as widening), and
  `scripts/packs/pack.mjs` for apps built outside Atelier. The link download cap
  rises to the app size limit for `.atelierapp` and `.atelierworld`.
- **Links**: `atelier://packs?install=<https url>` opens the review for any
  `.atelierpack`, `.atelierapp` or `.atelierworld` at that address.
- **File types**: `.atelierapp` and `.atelierworld` are registered in
  `electron-builder.yml` beside `.ateliercompanion` and `.atelierpack`, with icons
  from `scripts/app-icons/art.mjs`.

## The community index

The pack index format gains `kind` (`pack`, `app` or `world`), `image` (the
share image's address), `category` (games, tools, worlds, creative, learning,
productivity, companions, other), `size` and `color`, all optional, so older
indexes and older Atelier keep working. App files are too big for the index
repository, so they are hosted as release assets and the index lists their
addresses and hashes, as it already does for packs: `scripts/packs/pack.mjs
--entry <address>` prints an archive's entry, and `make-index.mjs` builds an
index from a folder and keeps entries hosted elsewhere.

- **Browse** (Packs › Browse) shows cards washed in each item's colour with
  its picture, what it is, its shelf, size and author, filtered by kind and by
  search; Install opens the same review as every other way in. Pictures are
  PNG or JPEG, fetched by main within the share image's size and handed to the
  page as data, so the page reaches no other site. A world's place that opens
  an app the person lacks opens Browse at that pack (`atelier.worlds.find`).
  Still to come: a detail page with the still and the worlds that open it.
- **Remix** works as for packs: a copy in `dev/` and a chat that edits it.
  A remixed world keeps its guests; a remixed app gets a `-remix` id.
- **What the author may share.** Their own art, sound and characters,
  characters made with Atelier's companion art (for Atelier, as its
  [licence](../ART-LICENSE.md) allows), assets they licensed, and
  open-licensed assets with their credits. Not
  assets taken from someone else's game, and not other games' or companies'
  characters, names or logos. The index's pull request checks cover
  signatures, hashes and file rules, as for packs; maintainers check the
  rest. A project that started from someone else's game can join with its own
  art in its place, or by asking players for their own copy's files (see
  *Your own files*).
- **Withdrawn items**: the index can list withdrawn ids (`"withdrawn": [{
  "id", "reason" }]`). Atelier stops offering them and their updates and shows a
  notice on installed copies; it never deletes anything. The notice clears
  once every index can be read and none lists the id. Indexes are read when
  you open Browse, and in the daily update check only if something you have
  came from an index, so no one else's Atelier fetches one in the background.

## Where apps and worlds show up

- The Packs page (`atelier://packs`): Installed, Drafts and Browse, Install from
  file… and Install from link… (a form that shows when asked for), and New app
  or pack… (a companion builds it from a starter). A pack with one app has
  Open on its row, and installing an app or a world ends in a toast with
  Open.
- **Open always works or says why.** Open on an app, a panel or a world turns
  its pack on when it is off. Only a pack that can't run says no, and it says
  why: its problem, the organisation's policy, or what it waits for (with Find
  it in Browse).
- Worlds is a built-in Atelier app (`atelier-worlds`, off until wanted): your worlds and
  the ones packs bring, Visit, Edit, Share… and New world.
- An app opens in a tab; a game can go full screen, and Esc comes back. Apps
  can be pinned in the sidebar like pack panels.
- The command bar opens apps and worlds by name, also while Worlds is off
  (Open Worlds), and "apps", "games" and "worlds" find the Packs page.
- Settings › Your data counts the packs folder; packs' model calls are their
  own kind (`pack`) in the usage ledger.

## Bringing a web project in

1. Build static files: any bundler's production output, Next's `output:
   'export'`, a game engine's web export. Root paths work when the pack has one
   app; with several, give each build a relative base (Vite's `base: './'`).
2. Replace server routes. AI routes become `atelier.ai`; rooms and signalling
   become a `network` host or Atelier Rooms; a phone controller page becomes
   the Atelier pad.
3. Nothing to do for inline scripts or styles in the build's HTML. A build that
   uses threads needs `"isolated": true`; one that uses `eval`, `"eval": true`.
   A compressed Unity build needs its decompression fallback on, since Atelier
   doesn't send compression headers.
4. Replace a native bridge (an Electron or Capacitor preload object) with
   `window.atelier` calls.
5. Write `atelier-pack.json` with `"build": "bundled"`, then build and sign with
   `node scripts/packs/pack.mjs <folder> <out.atelierapp> --key <key.pem>`.
6. Keep your own art and characters; let the cast or the kit stand in only where
   you want them. To publish, every file in the pack has to be yours to share.
   Data you can't share goes through *Your own files*.

## What's built

- **Apps in packs:** manifest v2 `apps` inside packs, the app CSP and
  permissions, big packs read from disk (streamed, with ranges and code
  cache), `run: app:<id>`, app rows in the sidebar, `.atelierapp` files, Share…
  with a still and a note, and the review sheet.
- **The plugin model:** per-pack scopes, `provides`/`uses` services, events,
  the surfaces table, `requires`, `use_app`, `atelier_inspect`, draft hot reload,
  asset slots and asset packs, optional permissions, developer mode and the
  background integrity check.
- **AI, files and notifications:** `ai` as a service (ask, stream, json,
  session, budgets), `guide`, `files` (with `files.own`) and scheduled
  notifications.
- **The kit and the cast:** Kit 1 (three.js and addons, `atelier-kit/character.js`
  and `guide.js`, the companion art), `atelier.cast` (members, pick, speak),
  starters, playtesting with frames as images, and the build guide in parts.
- **Your own servers:** an app's direct connections to its `network` hosts
  (fetch, WebSocket, EventSource, media) with the CSP, lockdown, handlers and
  proxy in step with its grants; `secrets` in the keychain, added to requests
  to their own hosts only; `env`; a linked folder's `.env` and localhost; and
  the key check on export.
- **Worlds:** the format, the `atelier-worlds` viewer and editor, `.atelierworld`
  files, guests, `atelier.worlds` and `atelier.world.context`, kit props and
  `atelier-kit/world.js`. Harbour town, with a café run by a guest, comes with
  the app.
- **The community index:** apps and worlds in the index (kind, picture, shelf,
  size, colour, withdrawn ids), Browse with filters and pictures, Get from a
  world's place, and `pack.mjs --entry` and `make-index.mjs` for apps and
  worlds.
- **Organisations:** `auth`, `connectors` in apps, policies (indexes,
  force-install, allow and block lists, trusted keys, permission ceiling,
  sideloading, `AppConfig`, `AiProvider`), private indexes and the audit log.

Not built yet: `realtime`, Atelier Rooms and the Atelier pad, which multiplayer
apps need.

## Open decisions

- **A plugin framework for the core ring**: Atelier's built-in features keep
  their own `Feature` hooks and registries instead of moving the main process
  onto a general plugin framework. A move would rewrite every feature's wiring
  and would not help the pack ring, whose code can't run in-process anyway.
  Worth looking at again if the core ring's registries start needing
  dependency-driven start-up among themselves.
- **Atelier Rooms**: running it means hosting, cost and abuse handling. Without
  it, multiplayer and the pad are only for apps that bring their own server.
- **AI budgets**: the default numbers, and whether the review card shows an
  estimated cost.
- **Kit 1 contents**: whether Rapier is in from the start (about 2 MB), and
  whether an editor library (Tiptap) joins for writing tools or stays with
  bundled apps.
- **Guests to companions**: whether a guest you like can become one of your
  companions (Make a companion, through the `.ateliercompanion` import path).
- **Size cap**: 300 MB per app is a starting value.

## Today's apps

Single-file apps from `build_app` keep working at `atelier-app://<uuid>/` with
their own partitions and versions, under today's rules: inline code allowed,
2 MB, no network, no `window.atelier` (`APP_CSP` in `src/shared/apps.ts`).
Share as pack already turns one into a pack: its inline scripts move into
files (`moveInlineScripts` in `src/main/packs/service.ts`) and it becomes a
panel. Turning one into a `kit` app instead, listed on the Packs page with
the rest, is still to come.

## Out of scope

- Custom 3D props or companion parts in packs: worlds and apps use the kit
  (as [packs.md](packs.md) already says for companion parts).
- Node, npm installs or native code inside apps.
- Persistent online worlds: a world is a file, not a server.
- Payments and in-app purchases.
- A hosted gallery with ratings and install counts (as for packs).
